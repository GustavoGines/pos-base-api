## 2. Logic Chain

1. In MySQL InnoDB, when multiple concurrent transactions execute `SELECT quote_number FROM quotes ORDER BY id DESC LIMIT 1 FOR UPDATE` on an empty table or on the end-of-table supremum record, InnoDB places shared gap locks.
2. When each transaction proceeds to execute `INSERT INTO quotes (quote_number, ...) VALUES (...)`, it requires an exclusive insert intention lock on that gap.
3. An insert intention lock conflicts with active gap locks held by other concurrent transactions, creating a circular wait graph.
4. InnoDB detects this deadlock, terminates one or more transactions, and throws `SQLSTATE[40001]: Serialization failure: 1213 Deadlock found when trying to get lock; try restarting transaction`.
5. Because `QuoteController::store()` at line 141 tests only `$isDuplicate = in_array($e->getCode(), [23000, '23000']) ...`, SQLSTATE `40001` / error `1213` evaluates `$isDuplicate = false`.
6. Therefore, the retry loop does not execute; the transaction is rolled back, and `QuoteController::store()` immediately returns an HTTP 500 error to the client with the database error message exposed.
7. Furthermore, the backoff formula `usleep(15000 * $attempt)` is deterministic. Two colliding requests wait the exact same duration and collide again. With `$maxAttempts = 3`, high concurrency bursts (5-10 requests) cannot reliably self-resolve.
8. By expanding the retry condition to include `40001`, `1213`, `Deadlock found`, and `Serialization failure`, adding randomized jitter, and increasing `$maxAttempts` to 5, the PoC proved 100% resolution (10/10 successes).
9. For Delivery Notes (P2.1), the implementation in `DeliveryNoteController.php` and `StockService.php` is completely sound: locks are acquired in ascending ID order, counter sales are detected and shielded from double deduction, and voiding restores inventory with exact precision.
